# 9 novembre — Revue de sécurité « des vendeurs payants arrivent »

Branche `claude/securite-9nov` (pas mergée). Revue défensive de NOTRE code : les
12 fonctions `api/`, `api/_lib/`, les migrations Supabase (RLS) et le pont de
l'extension. Question posée : **un vendeur peut-il voir, modifier ou faire agir
les données d'un autre ?** Aucun secret dans ce fichier.

## En une phrase

**Aucune fuite entre vendeurs trouvée dans le code** (lectures et écritures avec la
clé de service toutes cadrées par le propriétaire tiré du JETON, RLS par
`owner = auth.uid()` partout, SECURITY DEFINER avec `search_path` fixé et retirées
à PUBLIC). Quatre défauts réels corrigés (un relais ouvert vers Anthropic, une
liaison Vinted sans preuve, deux hygiènes), deux défauts qui demandent une
décision de Julien.

## Défauts trouvés, par gravité

| # | gravité | défaut | état |
|---|---|---|---|
| 1 | **moyenne** (route coûteuse sans frein) | `POST /api/ai` avec une clé dans le corps appelait Anthropic **sans session** : vrm.center servait de relais ouvert à n'importe qui (clé volée « blanchie » par notre adresse, temps de fonction payé sur le plan de Julien). | **corrigé** : session exigée pour tout POST (401 / 503 si la connexion ne répond pas), abonnement vérifié (402), clé ≤ 300 signes. L'app envoie toujours sa session : rien ne change pour elle. |
| 2 | **moyenne** (s'approprier le compte Vinted d'un autre) | `POST /api/vinted-connect` acceptait un jeton Vinted **décodé, jamais vérifié** : un JWT fabriqué à la main (`exp` lointain, `account_id` de quelqu'un d'autre, visible sur son profil public) était rangé dans `vinted_accounts` du vendeur. Avec l'unicité globale de la 023, le vrai propriétaire était ensuite refusé. | **corrigé** : rien n'est rangé tant que Vinted n'a pas rendu le profil avec ce jeton (Vinted vérifie la signature) ; un `account_id` du profil différent ⇒ refus. Route sans appelant dans l'app aujourd'hui. |
| 3 | faible | `GET /api/relais` : `lat`/`lon` partaient tels quels dans l'adresse de Nominatim (`48.1&q=…` y ajoutait des paramètres). | **corrigé** : des nombres bornés (±90 / ±180), sinon rien. |
| 4 | faible | `/api/ship-reminders` : la clé du cron comparée par `!==` (s'arrête au premier écart). | **corrigé** : empreintes comparées en temps constant (même règle que la clé du script Gmail). |
| 5 | **moyenne — DÉCISION** | **RLS laisse un vendeur écrire N'IMPORTE QUEL `vinted_user_id` dans `vinted_accounts`** (politique `owner = auth.uid()` : la ligne est bien à lui, mais le compte Vinted n'est pas prouvé). Le #2 fermait la porte du serveur ; la porte directe (PostgREST avec son propre jeton) reste. Conséquences mesurées dans le code : (a) avec la 023 appliquée, le premier qui déclare l'identifiant Vinted (public) d'un autre le bloque ; (b) l'essai gratuit est consommé par compte Vinted (`essais_gratuits` clé `vinted:…`, `lireVintedIds`) : un squatteur brûle l'essai de la victime ; (c) `vinted-pris` lui dirait « déjà pris ». **Aucune donnée de la victime n'est lue** (chaque capture est rangée sous le vendeur de la session ; les jetons du squatteur sont faux). | **non corrigé** (touche l'extension et la base). Correctif proposé : (1) un déclencheur `before insert or update of vinted_user_id` sur `vinted_accounts` qui refuse au rôle `authenticated` (seul `service_role` relie un compte) ; (2) l'extension relie un compte par une route serveur qui vérifie le jeton chez Vinted (`/api/v2/users/current` avec SON jeton, comme le #2) puis écrit avec la clé de service ; (3) la 023 seulement après. À trancher : faut-il le faire avant d'ouvrir l'essai gratuit à des inconnus ? (je pense oui). |
| 6 | faible — DÉCISION (déjà dit en 5.330) | La carte de connexion de l'extension vit dans une shadow root FERMÉE sur des pages TIERCES (vinted.fr, leboncoin.fr, ebay, vestiaire). Le champ n'est jamais lisible par la page, mais un écouteur `keydown` que la page a posé sur `window` en capture AVANT l'extension entend les touches (limite déjà écrite dans `vrm-badge.js`). | **non corrigé** : seul un `<iframe>` de l'extension isole vraiment, et il ne s'affichait pas sur Orion (5.328). Proposition : sur Chrome/Edge/Firefox, l'iframe `popup.html` (déjà ressource web) ; la carte en shadow root seulement sur Orion. Décision de Julien (confort Orion ↔ isolement). |

**CORS** (`api/_lib/cors-extension.js`) : seules les origines `*-extension://` et
`https://vrm.center` reçoivent `Access-Control-Allow-Origin`, jamais
`Allow-Credentials` ; toutes les routes exigent le jeton dans `Authorization`, pas
un cookie (les deux cookies HttpOnly `vrm_ebay_etat` / Discord ne servent qu'au
retour OAuth, en `SameSite=Lax`). **En-têtes** (`vercel.json`) : CSP stricte
(`script-src 'self'`, `frame-ancestors 'none'`), HSTS 2 ans, `X-Frame-Options:
DENY`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` — vérifiés
par `audit-entetes` / `audit-csp`, verts. **Secrets** : aucune clé renvoyée au
navigateur (`sante` ne dit que des oui/non ; `configuration-auth` refuse tout ce
qui n'est pas la clé `anon`) ; aucun `console.*` de jeton ou de clé (grep).
**PostgREST** : aucun `or=`/`in.` construit avec une entrée brute (recherche
réduite puis citée, identifiants validés par motif).

## RLS — ce que garantissent les fichiers

Test statique `scripts/tests/rls-migrations.test.mjs` (`node --test`) : 127
fonctions lues, 76 SECURITY DEFINER. Il vérifie : RLS activée sur toute table de
`public` ; `search_path` fixé sur toute SECURITY DEFINER ; chacune retirée à PUBLIC
(sinon anon l'appelle) ; une fonction ouverte aux connectés qui prend un uuid
contrôle son appelant (`auth.uid()` ou une aide qui le lit) ; un vendeur en
PARAMÈTRE (`p_user`, `p_owner`…) n'est rendu qu'à `service_role` ; aucune politique
PERMISSIVE `using (true)` ; aucune écriture rendue à anon ; `app_data` et
`vinted_accounts` : verrou anon (021), `owner` obligatoire, règles par
`owner = auth.uid()`. **Vert**, et `--prouve` (8 mutations, chacune rougit).

⚠️ Un fichier du dépôt n'est pas la base : à lancer **en lecture seule** dans
l'éditeur SQL de Supabase (aucune n'écrit) :

```sql
-- 1. Toutes les tables de public ont-elles RLS ? (attendu : aucune ligne)
select tablename from pg_tables where schemaname = 'public' and not rowsecurity;

-- 2. Politiques permissives ouvertes à tous (attendu : aucune ligne)
select tablename, policyname, roles, cmd, qual, with_check from pg_policies
 where schemaname = 'public' and permissive = 'PERMISSIVE'
   and (qual = 'true' or with_check = 'true');

-- 3. Politiques de app_data / vinted_accounts (attendu : owner = auth.uid() partout,
--    vrm_anon_ferme RESTRICTIVE pour anon)
select tablename, policyname, permissive, roles, cmd, qual, with_check from pg_policies
 where schemaname = 'public' and tablename in ('app_data', 'vinted_accounts') order by 1, 2;

-- 4. SECURITY DEFINER sans search_path fixé (attendu : aucune ligne)
select n.nspname, p.proname from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where p.prosecdef and n.nspname in ('public', 'sauvegarde')
   and not exists (select 1 from unnest(coalesce(p.proconfig, '{}')) c where c like 'search_path=%');

-- 5. SECURITY DEFINER exécutables par anon (attendu : aucune ligne)
select p.oid::regprocedure from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where p.prosecdef and n.nspname = 'public' and has_function_privilege('anon', p.oid, 'execute');

-- 6. Droits d'écriture de anon sur les tables (attendu : aucune ligne)
select table_name, privilege_type from information_schema.role_table_grants
 where table_schema = 'public' and grantee = 'anon' and privilege_type in ('INSERT','UPDATE','DELETE','TRUNCATE');

-- 7. Le défaut #5 mesuré : un compte Vinted déclaré par plusieurs comptes VRM
--    (attendu : aucune ligne ; sinon la 023 refusera de s'appliquer)
select vinted_user_id, count(distinct owner) from public.vinted_accounts
 where vinted_user_id is not null group by 1 having count(distinct owner) > 1;
```

## Extension (pont, scripts de contenu)

- `bridge.js` (sur vrm.center seulement) n'écoute que `ev.source === window`, ne
  relaie jamais `from`/`action` venus de la page ; le service worker revérifie
  l'origine (`ORIGINE_APP`, `new URL(...).origin` ∈ vrm.center / ancien domaine
  Vercel) pour `etat`, `cmd`, `exec`, `adresse`, `pdfLbc`, `authEtat` ;
  `onMessageExternal` refuse toute autre origine. La session ne passe que par le
  canal ADRESSÉ (identifiant d'extension), `authEtat` ne rend qu'email et
  identifiant, jamais le jeton.
- Scripts de contenu des sites tiers (Vinted, Leboncoin, Vestiaire, eBay) : `from`
  est toujours posé par l'extension (la page ne peut pas se faire passer pour le
  pont) ; ils ne font que relayer des captures, rangées sous le vendeur de la
  session. Garde-fous §3 intacts (garde par compte connecté dans l'onglet,
  50 actions/h/compte, requêtes une par une, pause 429/403) : rien modifié.
- `cancale-v67-ten.vercel.app` (origine encore de confiance dans le manifeste et
  `ORIGINES_APP`) redirige vers vrm.center (307, mesuré) : il appartient toujours
  au projet. ⚠️ Si le projet Vercel était renommé ou supprimé, ce sous-domaine
  deviendrait réservable par un tiers ⇒ le retirer du manifeste à la prochaine
  version d'extension.
- Aucune modification de l'extension dans ce chantier ⇒ pas de nouvelle version
  (5.332.0 reste libre).
