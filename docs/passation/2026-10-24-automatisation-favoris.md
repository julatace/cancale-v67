# Messages automatiques à la sélection de favoris — 24 octobre

Demande explicite de Julien : même message enregistré pour les favoris cochés, remise textuelle en pourcentage, intervalle fixe choisi, plafond de dix messages sur toute fenêtre de soixante minutes par compte. Le risque a déjà été accepté ; aucun camouflage de comportement ni délai aléatoire.

## Raccordement et exécution

Le retour réel v4 montre une création native `POST /api/v2/conversations` avec trois champs plats : `initiator`, `item_id`, `opposite_user_id`. Leurs valeurs ne sont pas présentes dans le diagnostic partagé. Le serveur lit la capture privée du propriétaire, et exige qu'une notification de favori prouve exactement le couple article/personne de cette création. Cette observation établit le rôle de `notification.user_id` pour la même forme de liens `/items/ID/segment/new` et les mêmes noms de paramètres. Aucun rapprochement par titre, photo ou pseudo. Sans correspondance, lancement refusé avec instruction d'ouvrir un favori présent dans la liste sur Vinted puis d'actualiser. Le champ `initiator` reprend la valeur observée, sans en inventer une.

Sélection de un à dix favoris de la capture courante ; historique complet toujours non vérifié. Le serveur relit les réglages sauvegardés et compare leur version canonique à l'aperçu du navigateur, pour refuser un aperçu périmé après modification dans une autre fenêtre. Message et cadence sont figés dans la file ; modifier les préférences ne change pas une file lancée. La remise est dans le texte, aucune offre native de prix n'est créée.

Le module `api/_lib/favoris.js` est servi par `/api/compte?mode=favoris&uid=…`, sans nouvelle fonction Vercel. Session Supabase vérifiée et compte Vinted lu avec le jeton du vendeur et filtre propriétaire à chaque commande. Le serveur ne contacte jamais Vinted.

`modifierNeutre` protège l'état par CAS sur une ligne neutre par UID Vinted : groupes de propriétaires privés, quota partagé entre tous les appareils, une seule réservation en cours, autorisation consommable une seule fois par le propriétaire et pendant soixante secondes. Aucun effet réseau Vinted dans une décision CAS. Une réservation compte dans le quota même si le transport échoue. Cadence fixe et dix tentatives sur soixante minutes glissantes ; les timestamps sont prolongés jusqu’à l’accusé, pour ne pas libérer trop tôt le quota d’une requête lente. Une incertitude interrompt tous les groupes du même UID jusqu’à vérification. pas de rattrapage en rafale. Dédoublonnage article/personne conservé, y compris pour les tentatives refusées ou incertaines. Une nouvelle sélection ne reprend jamais les restes d'une ancienne file interrompue.

Extension **5.215.0** : opération interne `/vrm/favoris`, jamais relayée comme URL native ; seule l'autorisation serveur est transmise par l'app. L'extension la consomme avec sa propre session VRM, reçoit le texte et les cibles du serveur, crée la conversation au format observé, puis lit le fil. Elle vérifie les identifiants exacts de conversation, article et interlocuteur, ainsi que la possibilité de répondre, avant de poster le texte. Elle revérifie aussi que l’autorisation est toujours active côté serveur ; les appels natifs de cette opération ont un délai maximum de douze secondes. Compte du cookie revérifié avant chaque écriture ; deux écritures consomment deux actions du plafond existant de vingt actions/heure. Les écritures automatiques ne sont jamais rejouées, même après un 401. Une réponse 2xx avec code Vinted zéro confirme l'envoi ; réponse absente, 5xx ou accusé non reconnu => incertain, arrêt sans rejeu. La création native générique reste interdite dans `EXEC_PERMIS`.

## Interface et limites concrètes

Messages → Favoris reçus → Afficher → cocher → enregistrer message/remise/intervalle → Lancer les envois sélectionnés. File repliée hors sélection et activité ; statuts, prochain passage, arrêt et clôture manuelle d'une vérification incertaine. Une clôture conserve le dédoublonnage, ne renvoie rien. Une tentative déjà partie peut aboutir après l'arrêt.

Cette version nécessite **l'écran Messages de VRM ouvert et visible**, avec l'extension à jour et le bon compte Vinted connecté. Changement d'écran, onglet masqué ou navigateur fermé suspend les prochaines tentatives. Retour sur l'écran : reprise de la file autorisée, sans redélivrer une réservation. Pas de moteur permanent en arrière-plan et pas de relais téléphone pour cette opération. Sans extension compatible, lancement désactivé. Les moteurs de recherche ne changent rien ; Chromium et le paquet Firefox sont compatibles avec le pont existant. Safari/iPhone nécessite une distribution d'extension distincte, pas validée pour cet envoi. Ne pas promettre une compatibilité universelle ni une absence de bannissement.

Capacité initiale : 500 couples article/personne conservés par propriétaire et compte ; blocage explicite si capacité dépassée, aucun effacement silencieux du dédoublonnage. Les groupes protégés sont effacés à la fermeture du compte VRM par CAS, sans toucher aux autres propriétaires ni aux timestamps du quota. L'index de propriétaires est modifié atomiquement avec le groupe. Un échec de ce nettoyage conserve le compte et annonce une fermeture incomplète.

Audits exec, cohérence, offres automatiques inchangées, ZIP, adaptation navigateurs et fermeture du compte ; build Vite et banc achats/messages complet avec lancement via le pont sur ordinateur et blocage sur téléphone sans extension.

Essais uniquement sur fixtures inventées : aucun message réellement envoyé et aucun jeton de vendeur utilisé pour écrire en production.
