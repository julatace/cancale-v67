## 1. Un seul PDF (`bordereauxUnPdf`, `vrm-pdf.js`, `pdf-lib.min.js`)

- **Bibliothèque** : pdf-lib 1.17.1 (MIT), le fichier `dist/pdf-lib.min.js` tel quel (déjà dépendance de l'app), aucune
  `eval`/`new Function` (vérifié) ; licences dans `pdf-lib.LICENSE.txt` (pdf-lib, pako MIT/Zlib, standard-fonts, upng ;
  tslib Apache 2.0 en tête du fichier). 525 Ko, **chargés à la demande seulement** : le fond l'injecte (avec `vrm-pdf.js`)
  dans le monde isolé de l'onglet vinted.fr du panneau quand il touche « Imprimer » (`chrome.scripting.executeScript`,
  `files`) — rien sur les autres pages.
- **Fond** : `bordereauxUnPdf` = `bordereauCarte` (les MÊMES gardes : onglet vinted.fr, compte de l'onglet, projections
  scalaires, « %PDF » exigé, e-mail d'un autre compte écarté) + l'injection. Lecture seule, aucune requête vers Vinted.
- **Panneau** (`imprimerBordereaux`) : 2 bordereaux ou plus ⇒ `__vrmAssemblerPdf` assemble, dans l'ORDRE de la sélection,
  chaque page de chaque bordereau copiée telle quelle (`copyPages`), et ouvre UN onglet « bordereaux-N.pdf » (visionneuse :
  imprimer). Un PDF abîmé, chiffré, vide ou de plus de 6 pages n'entre pas : ouvert à part, dit (« 1 bordereau illisible
  gardé à part »). Une commande sans bordereau n'entre jamais (« 1 sans bordereau : Vinted ne l'a pas encore fourni »).
  Navigateur qui refuse l'injection ⇒ un par un comme avant, dit. Un seul bordereau : ouvert directement.
- **Orion** : `scripts/tests/orion-base-validee.py` doit approuver les trois membres (`pdf-lib.min.js`,
  `pdf-lib.LICENSE.txt`, `vrm-pdf.js`, injectés par background.js, aucun bloc du manifeste) **au moment où l'intégrateur
  régénère les zips** — voir « Pas fait ».

- Fond : onglet vinted.fr seul, `confirme` exigé, déjà dans l'état ⇒ rien ; garde stricte (sécurité `vacances`, une

  `/settings/profile`. « Fait » seulement si la page a reçu la réponse de Vinted ET montre l'interrupteur dans l'état voulu ;

- Étape `vacances` (version des étapes 3) : UN interrupteur au nom exact « Mode vacances » (5 langues ; case, `switch`,

- ⚠️ **Jamais vu sur la vraie page** : l'adresse et l'interrupteur sont devinés d'après les conventions ; s'ils manquent,
  VRM s'arrête et le NOMME. Le faire UNE fois à la main fait retenir la page.

## 3. Réponses, offres acceptées, ventes obtenues (`noterReponsesFavori`, `src/favorisVentes.js`)

- Après un message PARTI (`noterEnvoiFavori` : conversation, acheteur, annonce, version, offre, **auto**), le fil passé
  sous les yeux de l'extension — capture de la page (`conversation`) ou relecture GET `/api/v2/conversations/{id}` de
  `vintedPage` (séquence, moteur d'offres) — **aucune lecture de plus** — met à jour l'envoi : `r` 1re réponse de CET
  acheteur (message ou SON offre) APRÈS l'envoi, jamais réécrite ; `oa` notre offre acceptée (statut 20) ; `ob` offre de
  l'acheteur ; `l` fil relu. Identité seulement (n° de conversation de l'envoi = fil ; acheteur de l'envoi = autre membre).
- Journal `favori_reponse` (annonce seulement ; la route « Ce que VRM a fait » ignore cette sorte : ce n'est pas un geste
  de VRM). Ligne pour l'app **`favoris_reponses_{uid}_{nav}`** (un écrivain) : par envoi `t, k, o, i, a, r, oa, ob, au, l`
  — des scalaires, ni texte, ni pseudo, ni n° de conversation (l'acheteur `a` est une identité, gardée pour « même acheteur »).
- **La règle unique** `attribuerVentesFavoris` (`src/favorisVentes.js`, recopiée dans background.js par
  `node scripts/audit-favoris-ventes.cjs --recopie`) : entonnoir contactés → réponses (sur fils relus) → offres acceptées
  → ventes, par compte et par version ; une vente attribuée à l'envoi le plus récent de LA MÊME annonce, avant la vente,
  ≤ 14 j, même acheteur si lu des deux côtés ; répartition « message seul · message + offre acceptée · offre de l'acheteur
  · sans contact » ; date incertaine ⇒ dans aucune fenêtre, dite (« au moins ») ; CA, bénéfice (prix − achat − frais, si
  l'achat est connu, « au moins … sur k de n »), délai moyen, remise moyenne (prix de l'annonce lu) ; moins de 3 cas ⇒ « — ».
- **Panneau** : Favoris → Réglages, chaque version « ✈ N · … · R réponses sur L relus (P %) · K offres acceptées » ;
  Favoris → **Statistiques** (7/30/90 j) : entonnoir, par compte, par version, répartition, délai (CA et bénéfice : dans
  l'app ; « sans contact » « — » : l'extension ne lit que les ventes des annonces contactées).
- **App** (Statistiques › Pilotage › Messages aux favoris, `ventesFavorisFenetre` de `src/aujourdhui/pilotage.js`) :
  « Taux de réponse » (était « à capter »), « Offres acceptées », « Ventes obtenues » (répartition), « CA des ventes
  obtenues » (bénéfice), « Contact → vente » (délai, remise), une rangée par version. Lectures : `favoris_reponses_*`
  (projection `id,e:data->e`), le relevé de Statistiques, `lireExtrasRepartition` (+ `buyer->>id` sur la MÊME lecture,
  + le prix de l'annonce).

- Par compte de ce navigateur : actions heure/jour face aux plafonds (SA cadence), favoris contactés (heure/jour), refus

- Lecture locale seule (30 s de mémoire), rien chez Vinted, rien dans les plafonds. Publiée dans la réponse `etat` de
  l'extension (`sante`) : l'app (page Extension, groupe « Santé des comptes ») l'affiche sans rien recalculer.

## 5. Favoris en 4 étapes, et l'automatique

- « Envoyer à N » ouvre **1 Sélection · 2 Réduction · 3 Message · 4 Lancer** (barre d'étapes, « Étape n sur 4 · … »,
  « Suivant » / « Retour » ; Retour garde tout). 1 : les favoris choisis (« Retirer »), le compteur et le plafond, les
  sautés comptés par raison ; 2 : taux 5/10/15/20/libre, « 59 € → 53 € », remontées au plancher en ambre, « Valider la
  réduction » ; 3 : le message EXACT pour le favori 1 sur N (‹ › pour les suivants, rendu par le fond pour CE favori),
  « Modifier pour cet envoi », « Choisir une autre version », « Enregistrer comme modèle », « Valider le message » fermé
  tant qu'il serait refusé ; 4 : récapitulatif (N · −t % · message · rythme · « 15 maintenant, les R autres à HH:MM »),
  « Lancer l'envoi (N) » — le chemin `lancer` de toujours, avec le taux et le texte VALIDÉS ; 1er message tout de suite.
  Dernier choix gardé par compte (`vrmFavEtapes` : taux, message de l'envoi/version, rythme).
- **Automatique** : allumé pour ce compte ⇒ les nouveaux favoris reçoivent le message par le pilote (inchangé), avec les
  réglages ENREGISTRÉS ; en haut de Favoris, toujours : « Automatique : allumé · −10 % · 3 versions · 15/h » et
  « Modifier » (étapes 2-3 sur les réglages enregistrés, exemples pris dans la liste, « Enregistrer » = `reglagesFavoris`,
  rien n'est envoyé). Allumer (Automatisations → Favoris) montre UNE fois le récapitulatif (taux, message rendu sur un
  exemple, plafonds, plancher) avant « Oui, allumer ». Les envois automatiques sont marqués `au` (statistiques « dont N
  automatiques »).
